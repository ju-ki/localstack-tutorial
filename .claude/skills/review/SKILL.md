# 学習用コードレビュー

学習者が自分で書いたコードをレビューする。目的は「正しいコードにすること」ではなく、**学習者が自分で問題に気づき、直し方を考えられるようにすること**。CLAUDE.md の基本姿勢に従う。

## 手順

### 1. 対象を決める

- 引数でファイルやフォルダが指定されていればそれを対象にする。
- 指定がなければ `git status` と `git diff`（未コミットの変更）を確認し、変更されたファイルを対象にする。変更がなければ、直近のコミット（`git log -1 -p`）を対象にしてよいか学習者に聞く。
- 対象が多い場合は、どれから見るかを学習者に選んでもらう。

### 2. 先に学習者の意図を聞く

コードを読む前に、次の2つだけ短く聞く（すでに説明されていれば省略）。

- このコードで何をしたいか（どの Day の課題か、何を作ったか）
- 自分で気になっている点や自信がない点はどこか

### 3. コードを読み、観点ごとに確認する

以下の観点で読む。該当しない観点は飛ばしてよい。

| 観点 | 見るポイント |
| --- | --- |
| 動作 | 意図どおりに動くか。エラー処理の漏れ、境界値、非同期処理（`await` 忘れなど） |
| AWS の使い方 | 正しいサービス・API・オプションを選んでいるか。リソース名やリージョン、ARN の扱い |
| IAM・セキュリティ | 権限が広すぎないか（`*` の多用）。認証情報やシークレットをコードに直書きしていないか |
| LocalStack と本番の違い | エンドポイントのハードコード、LocalStack でしか動かない前提、本番に移すと壊れる箇所 |
| 読みやすさ | 命名、関数の分け方、重複。TypeScript なら型の付け方 |
| 再現性 | 手順が README などに残っているか。他の人（未来の自分）が同じ環境を作れるか |

### 4. 指摘を整理して伝える

指摘は重要度順に並べ、**一度に出すのは最大3つ**まで。残りは「他にもいくつかある」とだけ伝え、学習者が求めたら続きを出す。

各指摘は次の形で書く。**直したコードは書かない。**

```
### 指摘1: <短いタイトル>（重要度: 高 / 中 / 低）
- 場所: path/to/file.ts:12
- 何が起きうるか: <この書き方だとどんな問題につながるか>
- 考えてほしい問い: <学習者が直し方にたどり着くための問い>
- 参考: <関連する AWS / LocalStack 公式ドキュメントの章やページ名>
```

良かった点も1つ以上、具体的に伝える（「エラー処理が丁寧」ではなく「S3 の `NoSuchKey` を個別に扱っていて、404 を返す設計になっている」のように）。

### 5. 理解を確認する

レビューの最後に、コードの中で鍵になる部分について1つ質問する。

- 例: 「この Lambda に付けた IAM ロールで、DynamoDB のどの操作ができてどの操作ができないか説明できますか？」
- 例: 「`--endpoint-url` を外して本番 AWS に向けたら、このスクリプトはどこで何が変わりますか？」

学習者が答えたら、合っている部分を認め、ずれている部分を具体的に伝える。

### 6. 修正後の再レビュー

学習者が直したら、前回の指摘ごとに「解決した / まだ残っている / 別の問題が出た」を確認する。解決していれば、なぜその直し方で良いのかを学習者自身に一言で説明してもらう。

## ヒントの段階

学習者が直し方に詰まったら、CLAUDE.md の「ヒントの出し方」と同じ段階で進める（方向づけ → 考え方 → 部分的な例 → 完全な例）。完全な修正コードは、学習者が明示的に求めたときだけ出す。

## 例外

次のものは学習の本題ではないので、指摘と一緒に直し方をそのまま示してよい。

- タイポ、構文エラー、import 漏れなどの単純なミス
- Docker / docker compose など環境構築まわりの設定
- 学習者が「今回は直したコードも見せて」と明示した場合
